# run393 panic 与第 212 槽推进

照片显示 Break 0x1 异常，PC 还原为 `0xfffffff007a39cc0`。run393 的符号表将该地址精确映射到 `NativeHoujiLegacyDisplay::opaque212()`，源码为 `__builtin_trap()`。这次直接触发原因是后端未实现槽，不是 run392 的 provider 空指针。

Ubuntu 最新已有 `/tmp/kernel-log-1115-0125.txt`、`/tmp/console-log-1115-0125.txt`，两者仍只保留环形窗口末段，没有早期发布检查点。当前 USB 未连接，未再获取新的日志窗口。不能单凭这些日志声称模式配置或首帧已成功；但 PC 已能确定执行进入派生类的第 212 槽。

## ABI 证据

原版 family 的调用链为 `0xfffffff004c00c04` → `0xfffffff004bfec14` → 虚表偏移 1696（212×8）。包装器给槽函数传入一个 32 位查询值、一个指向本地 32 位计数的指针，以及结构输出指针；返回值按 32 位 IOReturn 消费。随后将计数零扩展到 64 位 scalar output。

dispatch entry 位于 `0xfffffff005ded248`，字段为：函数 `0xfffffff004c00c04`、scalarInputCount=1、structureInputSize=0、scalarOutputCount=1、structureOutputSize=64。

具体查询的业务含义仍未定名，不能声称已经实现显示模式或硬件能力。此轮使用中性方法名 `queryBackendCapability`，只落实经审计的调用约定和明确的错误返回。

## 改动

- ABI 头生成器将第 212 槽替换为 `IOReturn(uint32_t, uint32_t *, void *)`，保持 338 槽布局不变。
- 派生类移除该槽的 trap，检查指针，将输出计数置零，返回 `kIOReturnUnsupported`；不猜测或写入未知的 64 字节输出结构，不伪造成功。
- 前 8 次调用记录 `stage=backend-query slot=212 query=… rc=unsupported`。
- ABI 审计脚本加入 dispatch entry、参数转发、虚表偏移及结果零扩展的逐指令检查，避免工具链接受未经核实的接口签名。

本地验证：两处驱动 ARM64 对象编译检查通过；像素、队列、请求三组既有测试通过；完整静态 ABI 审计通过。普通 clang 的 allocator builtin 使用 layout-only shim，完整 Apple 工具链链接另由 CI 验证。
